# L2 原生工具调用 A/B（2026-10-02 ～ 10-03）

**问题**：L2（Office COM）一直是"模型一次输出整组 JSON 操作、执行结果不回给模型"。
换成原生 function calling + 多轮回喂，值不值？

**一句话结论（截至第四轮；模型对比见三·六）**：布局要读了才知道的任务上，多轮有真实收益，两次留出集结论一致
（第三轮 6/10 对 0/10，第四轮 5/10 对 0/10）；布局已知的任务上没有收益（原 semi 三条两臂都是 15/15），
而 token 贵约 21 倍、耗时约 2 倍。**默认仍是 json**。
（这是第四轮时的结论。之后做了按任务自动挑（三·七），**10-03 起产品默认改为 auto、多轮用 glm-5.3**，见五。）
A/B 过程中还挖出了十多个"零报错、但整件事是错的"缺陷，其中 `write_range` 多行写入只写一格从 M1 起就在。

## 一、设计

### 三臂（`--l2-tools`，同一条任务在三种方式下紧挨着跑，同一时段采集）

| 臂 | 做法 |
|---|---|
| `json` | 一次输出整组 ops，执行结果不回给模型（M0 起的做法，默认） |
| `native-once` | 原生调用，但只给一轮：全部调用 + finish 一次给齐 |
| `native` | 原生调用 + 多轮：真实结果以 `role=tool` 回喂，直到 finish |

中间那臂的作用：json → native 同时换了两样东西（输出格式、有没有回路），只比两头说不清改善来自哪一样。

两臂看到的是**同一套工具**（名字、说明、参数由 `TOOLS` + `TOOL_ARGS` 同出一源，测试守着）。

### 任务（都不在 20 条主任务集里，避免改变已发表数字的分母）

| 集合 | 任务 | 说明 |
|---|---|---|
| 开发集 | `excel_formula` / `excel_recalc` / `excel_pdf` | 原 semi 分档三条，布局在提示里说清了 |
| 开发集 | `excel_formula_layout` / `excel_lookup` | 布局藏起来：表头在第 3 行、编码在 B 列不在 A 列 |
| 第三轮留出集（第四轮起降为开发集） | `excel_sumif` / `excel_total_row` | 第三轮开跑前写好并冻结 |
| **第四轮留出集** | `excel_rank` / `excel_countifs` | 第四轮的实现改动全部做完之后写、写完冻结 |

所有判据都做了三个方向的自检：空工作区判错、参考解判对、"凭习惯猜布局"的错误答案判错。
每次留出集的冻结都有 SHA-256 为证：开跑前记录实现和任务文件的哈希，跑完复核一致。
一组留出集只能用一次：看过它的结果、据此改了实现，它就降为开发集，下一轮另写新的。

## 三、第三轮结果

### 成功率

| | json | native-once | native |
|---|---|---|---|
| 留出集 | 0/10 | 0/10 | **6/10**（sumif 5/5，total_row 1/5） |
| 开发集 | 13/25 | 5/25 | 12/25 |
| 其中原 semi 三条 | 13/15 | 5/15 | 12/15 |
| 步骤走到了 L2 的 | 13/34 | 5/31 | 18/30 |

- 留出集 native 对 json：Fisher 精确检验 p ≈ 0.011。**但 6 次通过里 5 次来自 sumif 一条任务**，
  样本只有两条任务 × 5 次，结论只到"有收益的迹象"，不到"稳定提升"。
- 开发集两臂无差别（p = 1.0）。原 semi 三条上 native 少的那 3 次**全是规划器把任务拆成两步、
  两步都被路由给 L1**，和工具调用方式无关（三臂都有：json 1、once 4、native 5）。

### 代价（只算 L2 那一步）

| | json | native-once | native |
|---|---|---|---|
| token 中位 | 880 | 1823 | 20642（≈ 23×） |
| 耗时中位 | 5.8s | 1.3s | 10.3s |
| 模型轮数中位 | 1 | 1 | 9 |

贵的主要原因：**GLM 习惯一轮只发一个调用**（open → 列表 → 读 → 读 → 写 …），
每轮都要重发完整对话和 16 个工具定义。提示词里写了"互不依赖的调用放在同一轮"，效果有限。

### 出错方式

| | json | native-once | native |
|---|---|---|---|
| 工具执行报错 | 13 | 0 | 33 |
| 报错后这一步仍做成 | 0 | 0 | **8** |
| 没调 finish、按已执行写操作收尾 | 0 | 5 | 4 |
| 参数不是合法 JSON / 调用漏进正文 | — | 0 / 0 | 0 / 0 |

- 多轮的价值在第二行：**json 报错就是失败，多轮有 8 次自己改对了**。
- `native-once` 0/25 → 5/25 全靠"收尾"规则：它几乎每次只发一个调用就停了 ——
  提示词明确要求一轮给齐，GLM 仍然一轮一个。**只换格式、不给回路，在 GLM 上比 json 更差**。
- 原生调用这一侧 0 次参数损坏、0 次漏进正文。json 这一侧本轮 1 次解析失败、0 次需要修补 ——
  这个模型上"格式稳定性"不是瓶颈。

### 源数据完整性（审计，不改判据结论）

判据只看"该写的写对了没有"，不看"不该动的动了没有"。从轨迹里的写操作反推落点、和夹具比：

| | json | native-once | native |
|---|---|---|---|
| 改动了原有数据的运行 | 5 | 0 | 5 |
| 其中判据照样通过 | 0 | 0 | **1** |

10 次逐条核对过，都是真覆盖：json 5 次是看不见布局、把 SUMIF 写进了「金额合计」表头；
native 4 次是读了表却数错一行、压掉了「人事部」，1 次是漏写 sheet 参数、把公式写进了「流水」源数据表
——**那一次判据通过了**。

**两臂都会破坏数据，方式不同：json 是因为看不见，多轮是看了之后数错、漏参数。**
回路给了模型改错的机会，也给了它更多乱动的机会；收益要靠工具层的护栏才拿得住，提示词拿不住。

## 三·五、第四轮（方案 B：先把已知问题收尾）

**第三轮之后改的**（每一条都来自第三轮逐条看轨迹的结论）：

| 问题 | 改法 |
|---|---|
| `set_formula` 新措辞让 json 只写 D2 | 说明改成"只写 cell 指定的格子；要一整列就给整片区域" |
| 判据不看"不该动的动了没有" | A/B 专用任务加 `untouched`：重建夹具逐格比，允许区域之外任何变化判失败（20 条主任务判据不动） |
| 读回是裸二维数组，模型数错行 | 每个值带地址（`A3=部门 \| B3=预算`） |
| 覆盖已有数据无人拦 | 覆盖已有数据要 `overwrite=true`；拿数值/空值盖公式一律拒绝；补齐短行的 None 也算写入 |
| 规划器拆出的"写公式"步不带文件名，L2 认不出应用、让路搁浅 | 这一步明确要引擎时，L2 从总任务里认应用（只在这种情况下，避免抢 L1 的活） |

路由那条改动单独做了回归：local + semi 两档 11 条 × 2 次，判据 22/22、路由 22/22（含 L2 不许抢活的反向对照）。

**结果**

| | json | native-once | native |
|---|---|---|---|
| 第四轮留出集（rank / countifs） | 0/10 | 0/10 | **5/10**（countifs 5/5，rank 0/5） |
| 开发集（7 条） | 15/35 | 5/35 | **27/35** |
| 其中原 semi 三条 | **15/15** | 5/15 | **15/15** |
| L2 token 中位 / 耗时中位 / 轮数中位 | 979 / 3.8s / 1 | 1895 / 0.9s / 1 | 20990 / 8.1s / 8 |
| 工具报错后仍做成 | 0 | 0 | 5 |
| 改动了原有数据（审计） | 10 | 0 | 4 |
| 其中判据照样通过 | 0 | 0 | **0**（新判据堵上了第三轮那个盲区） |

- 留出集 native 对 json p ≈ 0.03，开发集 p ≈ 0.007。开发集的提升里有本轮修复的功劳，只能当开发集看。
- json 的回归修好了：原 semi 三条回到 15/15。
- **rank 三臂全是 0/5，原因不在 L2**：规划器又把"加表头"拆成单独一步、交给了 L1。
  native 那几次 L2 写的排名公式全对（E3:E10 = 5、2、7、4…），表头却被 L1 写在了第 1 行；
  json 那几次更糟 —— **L1 用 pandas 整个重写了文件，工作表名变成 Sheet1、表头变成 `Unnamed: 1`**。
  这是 L1 的问题，影响面不止这次 A/B（见第五节）。

**第四轮看出来的新问题**（尚未修，留作下一轮）：

1. **`overwrite` 被模型习惯性带上**：几乎每次写入都附 `"overwrite": true`，连空格子也带。
   native 那两次把 SUMIF 写进「流水」表的，都是带着它过去的 ——
   **模型能自己给自己的确认，就不是确认**。要改成"必须点名要覆盖的格子"，或者交给人确认。
2. **不写 sheet 时写进"活动表"**：多表工作簿的活动表是第一张（「流水」），不是模型正在操作的那张。
   要改成"工作簿有多张表时，写操作必须指定 sheet"。
3. **读回不告诉模型"下面还有数据"**：layout 那次只读到第 10 行、数据其实到第 11 行，少写一行。
   读回时应附上工作表实际用到的范围。
4. **L1 用 pandas 重写 xlsx 会毁结构**（表名、格式、表头行）：比 L2 的问题影响面更大，要单独处理。

## 三·六、修完第四轮问题之后：三个模型对比（2026-10-03）

**先修的**（第四轮暴露的问题）：L1 改已有 xlsx 前后核对结构、毁了就还原并回喂；
覆盖确认改成"知情确认"（要写出被覆盖格子现在的内容）；多表工作簿写操作必须给 sheet；
读回提示"下面/右边还有内容"；`set_formula` 必须以 = 开头。
另修了一个换模型时的隐患：`--model` 覆盖时思考参数沿用了 .env 里旧模型算出来的值
（换 glm-5.3 直接 400；glm-5.3-flash 收下 `disabled` 却照样思考、不报错）。
GLM-5 系列现在默认 `thinking=enabled + reasoning_effort=low`（官方默认是 max）。

**设计**：3 个模型 × json / 原生多轮 × 11 条 × 3 次 = 198 次。11 条里有 2 条
（`excel_share` 占比、`excel_avg_block` 找汇总块）是实现定稿之后才写的新题 ——
其余 9 条都是对着 glm-4.5-air 的失败调过实现的，单拿它们比会偏向 glm-4.5-air。
三个模型依次跑（跑批器一批只能一个模型），实现文件开跑前后 SHA-256 一致。

**读法**：

1. **json 方式和模型无关，卡在结构上**：三个模型都是 9/33，过的正好是"布局已知"那 3 条。
   看不见表，换多强的模型也只能猜。
2. **原生多轮 + 更强的模型 = 11 条全对**，包括两条没人见过的新题。
   glm-4.5-air 输在 rank（3 次都把排名写进了「备注」列 / 标题行）和 layout 一次漏写表头。
3. **更强的模型反而更省 token**：轮数从 9 降到 5（先把要读的一次读齐、几乎不报错），
   一步 token 减半。**但更慢**：单次调用要思考，glm-5.3-flash 一步 21.7 秒、glm-5.3 12.8 秒，
   glm-4.5-air 7.8 秒。价格页是前端渲染的、抓不到单价，实际花费以控制台账单为准。
4. **"一轮只发一个调用"的习惯，更强的模型基本还在**：glm-4.5-air 真实任务里一轮多调用 0%；
   glm-5.3 8%、glm-5.3-flash 15%，而且几乎都是"两张表一起读"这一种。
   （探针那种玩具例子里三个模型都会并行发两个 —— 真实任务里不会，单看探针会得出错误结论。）
5. **知情确认挡不住照抄**：glm-4.5-air 那次"判据照过但改了原数据"，是把拒绝信息里给的
   `{"A1": "品名"}` 原样抄进 overwrite，把表头改成了 `=1` 又写回 `="品名"`。
   护栏只能减少事故；**覆盖用户数据最终要交给人确认**（做 MCP 时接入确认机制）。

**样本**：每格 3 次，结论是方向不是精确百分比；三个模型不是同一时段交错采集。

## 三·七、按任务自动挑工作方式（`--l2-tools auto`，2026-10-03）

**怎么挑**（不调模型，先用 openpyxl 看一眼目标工作簿）：只有两种情况走 json —— 不用按内容定位的操作
（导出、另存、重算），或者任务写明了位置**且**表格是标准布局（一张表、表头在第 1 行、从 A 列起、
中间没有隔开的块）。其余一律多轮。json 执行中途报错：把文件还原成执行前的字节，改走多轮重做，
两次的账并在一起报；越界、用户拒绝了覆盖、工作区里有用户自己开着的文档，这三种不兜底。
多轮那条路单独配模型（`--l2-native-model glm-5.3`），json 和其余环节仍是 glm-4.5-air。

**第一轮**（15 条 × 3 次；其中 4 条是 auto 定稿后新写的）：json 8/45、多轮 42/45、**auto 42/45**，
L2 token 中位 1027 / 11061 / 9512。暴露两个问题，都已修：
1. **json 开始猜表名**：上一轮给工具说明加了"多表时必须给 sheet"，json 看不见表就每次带一个 "Sheet1"，
   而 openpyxl 建的表叫 "Sheet" —— 两条"位置写明"的新题 json 0/3，WPS 只回「发生意外」。
   改：只有一张表时名字写错就用那唯一一张（结果里说明），多张表时报出实际有哪几张。
2. **"加表头"被拆出去以后路由乱了**：没提文件名的「在D1单元格添加表头」被 L3 拿前台终端窗口接走、
   再上浮给 L4 去点资源管理器；提了文件名的交给 L1，它把整列「费用」改成了公式。
   改：总任务要 Office 引擎时，同一本工作簿上的结构增改（加表头、加列、写函数）一律归 L2，L1 让路；
   "函数"补进引擎词表。纯数据清洗仍归 L1（有反向测试）。

**第二轮**（17 条 × 3 次；前 15 条已降为开发集，另写了 2 条新题开跑前冻结）：

| | json | 多轮 | **auto** |
|---|---|---|---|
| 全部 17 条 | 17/51 | 50/51 | **50/51** |

## 四、A/B 过程中挖出的缺陷（全部已修，均有测试；变异测试确认测试能抓住）

| # | 缺陷 | 影响 |
|---|---|---|
| 1 | **`write_range` 多行写入只写一格**：pywin32 晚绑定把 `Range.Resize(8,1)` 解析成"取 Resize 再按 `Item(8,1)` 取一格"，整块数组塞进右下角，返回"写入 8×1 区域"、零报错 | M1 起就在。查了轨迹库：历史上的 json 运行从没用过多格写入，**已发表数字不受影响**；只有今天的 native 运行撞上 6 次 |
| 2 | 回滚时文件被 WPS 独占锁住 → `copy2` 抛异常 → 整次运行崩溃，库里那条永远停在 running | json 同样会撞上，只是旧任务从没在打开文件后中途失败过 |
| 3 | 公式出错时 COM 返回 `-2146826246` 而不是 `#N/A` | 模型看不出自己错了；修后冒烟里它看到 `#N/A` 就把查错的列改了过来 |
| 4 | 轮数用完判失败 → 回滚删掉正确产物 | M0 那条"回滚权限只配给执行中途失败"的教训换了个地方重演 |
| 5 | 公式算出错误值记成成功 → 止损器看不见、源数据被改坏后保留 | 同上一条的反面：不回滚也有代价，所以"收尾"必须带条件 |
| 6 | `write_range` 把公式写死成数值 | 判据认得出；真实用户那边没有判据 |
| 7 | `export_pdf` 写出扩展名是 `.xlsx` 的 PDF | 通道自己的校验（文件在、非空）照过不误 |

另外两处探针级发现（`spikes/SPIKE_REPORT.md` 末节）：智谱 `tool_choice` 传 `required` / 指定函数时，
返回 200、`tool_calls` 为空、调用以模板文本漏进正文（已识别为 `tool_leak`、不开放该参数）；
发起调用时正文不是空串。
