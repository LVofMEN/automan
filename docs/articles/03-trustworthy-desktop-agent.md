# 让一个会动鼠标的 Agent 值得信任：沙箱、确认、回放与打包

> AutoMan 技术文章 · 第 3 篇 / 共 5 篇

前两篇讲的是"它做得对不对"。这一篇讲另一个问题：**一个会真的动你鼠标、改你文件、
替你点"提交"的程序，凭什么让人放心装在自己电脑上？**

我的回答是四样东西：边界（它能碰什么）、确认（撤不回的事谁说了算）、
回放（事后能不能看清它干了什么），以及一个**在别人机器上也照样成立**的安装包。
每一样都在做的过程中被真实的 bug 教育过，下面按这个顺序讲。

## 一、边界：沙箱防的是"写错了"，不是"想使坏"

L1 这一层让模型生成 Python 代码去处理文件。生成的代码跑在一个子进程里，
进程里装了一个 Python 审计钩子（`sys.addaudithook`）：

- 写文件、删除、改名只许落在工作区里；读文件只许读工作区和 Python 自己的库；
- 起子进程、联网一律拦；
- **ctypes 一律拦** —— 放开 ctypes 等于放开一切，它能直接调 Win32 API 绕过上面每一条。

最后一条有个麻烦：pandas 自己导入时就要用 ctypes 加载系统 DLL。按库名放行等于把最该拦的放进来。
解法是**时序**：白名单里的库在装钩子**之前**就导入完，它们的 DLL 加载发生在钩子生效前；
模型的代码再 `import pandas` 时只命中模块缓存。于是 ctypes 对生成的代码始终是封死的。

这道沙箱我在文档里写得很直白：**它防的是模型写错了，不是蓄意攻击。** 审计钩子不是安全边界，
真正兜底的是另外两条 —— 写之前自动把工作区备份一份，以及下一节的确认。

## 二、确认：撤不回的事，人说了算

删除、提交、发送这类动作，执行前必须停下来问人。这件事的难点不在"弹一个框"，
而在几个很容易做错的细节：

**默认是"否"。** 终端里是 `确认执行？(y/N)`，直接回车不算同意。客户端的确认卡片上，
回车键被显式吞掉，Esc 等于"不执行"。一个会自动操作的程序，最不该出现的就是"顺手一个回车就放行了"。

**答案要对得上问题。** 客户端和内核之间用一行文本协议传递确认：内核在标准输出里打一行
`@@automan.confirm {…}`，客户端把答案 `{"id": …, "ok": true}` 写进子进程的标准输入。
判定是严格的：id 必须对得上，`ok` 必须**恰好是** `true`；空行、超长、不是 JSON、id 不对、
管道断了 —— 一律按拒绝处理，并写明是哪一种拒绝。

**批准之后，前台要还回去。** 这是最隐蔽的一条。一步如果没有指定窗口，L3/L4 操作的是
"当前的前台窗口"。可人为了确认，得点一下确认卡片 —— 前台就变成了确认卡片所在的窗口。
不把前台还回去，刚批准的那个不可逆动作就会落在**终端或 AutoMan 自己的窗口**上。
所以放行之后，内核先把前台交还给确认之前的那个窗口；**交还不了，就按拒绝处理**。
人批准的是"对那个窗口做这件事"，不是"对随便哪个窗口做这件事"。

**放行也要留痕。** 被拒绝的步骤会带着"未获授权"进库；而被批准、真的执行了的不可逆动作，
早期在库里就是一行普通的"成功" —— 谁批的、前台有没有交还，一个字都没有。
复盘时最该查的恰恰是这一类。现在它们带着放行记录，界面上标"人工放行"。

**执行到一半也会问。** 后来 L2 改成"先读表、再写"的多轮方式之后，出现了一类新动作：
写入会盖掉用户已有的数据。第一版让模型带一个"我知道要覆盖"的标记，它几乎每次都带；
改成"写出被覆盖格子现在的内容"，它又照抄拒绝信息里给的内容绕了过去。
**模型能自己给自己的确认，就不是确认。** 现在这类写入走和删除、提交同一条确认通道，
问题写成"覆盖「工资.xlsx」的「工资」表里已有的数据：D2（现在是「7000」）……"，人说了算；
跑批时自动放行，评测数字不受影响。这件事的来龙去脉在[第 4 篇](04-look-before-you-write.md)。

## 三、回放：推出来的东西必须说是推出来的

客户端**不改写执行记录**：发起任务是起一个子进程跑命令行，自己只轮询数据库。
这换来三件事：命令行跑过的任务在界面里照样能回放；界面崩了不影响正在执行的任务；
评测台和客户端看到的是同一份事实。代价也接受：中途停掉的任务，在库里会一直是 `running` ——
界面不去替内核补写一个它没说过的结局，宁可留一条看得见的残留。
后来加了回收站，界面才第一次写库，而且只写一列：删除 = 记下扔进回收站的时刻，恢复 = 清掉它；
只有用户点"清空"才整行删除。每一步做了什么、错在哪、花了多少，这些列它一个字不碰。

视觉那一层的回放，要把每一轮的截图、模型的想法、点击位置画在一起。难点是**历史数据不完整**：
早期版本只在成功的步骤上记了截图目录，库里 654 个视觉步只有 317 个知道自己的截图在哪 ——
而最需要回放的恰恰是失败的那些。

往后修很简单：每一条出口都带上证据指针。往回补就得推：按时间把截图目录和步骤一对一配起来
（这条规则在那 317 个已知答案上 317/317 配对正确，才拿去推剩下的）；点击位置按可信度依次推 ——
模型给的归一化坐标、这一步自己记下的窗口矩形、同一次运行里别的步的窗口矩形、按截图尺寸查到的矩形；
**推不出来的不画**，并写明有几个没画。

推出来的位置在界面上画**虚线圈**，鼠标停上去能看到它是怎么来的。
1802 次历史点击里能画出来的是 1204 次，没有一次落在图外。
**不画比画错好；画了推测的，就要说是推测的。**

## 四、打包：只在别人机器上才会坏的那些事

便携包用 PyInstaller 打，解压即用、不需要装 Python。这一步踩的坑，全部是
**"在开发机上一切正常"** 的那一类：

- **`sys.executable` 变了。** 源码运行时它是 Python 解释器；打包之后它是 exe 自己。
  客户端起命令行、命令行起沙箱，两处都拿它当解释器 —— 断的是 L1 这层最便宜、用得最多的。
  现在所有子进程都向一个模块要命令行，并有一条测试禁止其他地方再碰 `sys.executable`。
- **编码。** 打包后的程序忽略 `PYTHONIOENCODING` 这类环境变量：命令行的输出变成 GBK，
  客户端按 UTF-8 读就是乱码；更糟的是沙箱里不写 encoding 的 `open()` 会按 GBK 读中文 CSV ——
  不报错，读出乱码。两个 exe 都打进了 UTF-8 模式，沙箱入口没开 UTF-8 就拒绝启动。
- **惰性导入。** 第一次在解压出来的包里真跑任务就失败了：pandas 写 xlsx 时才去导入子模块，
  打包版要从 exe 内嵌的归档里读 —— 被沙箱判成"读越界"。修法是只放行**读 exe 这一个文件**。

这三个问题的共同点是：**打包本身不报错。** 所以打包脚本最后一步是用打出来的 exe 跑自检，
而自检的每一条都是**实测，不看开关**：真跑一段沙箱代码、真做一次中文文件往返、
往 `PYTHONPATH` 里塞一个标记看注不注得进去、真做一次"CSV → pandas → xlsx → 读回"。
我拿去掉修复的代码打过一次包，确认自检会报红、打包会停。

**干净机器上缺不缺 DLL**，同样不能靠"在这里跑得起来"来判断 —— 开发机装过 VC++ 运行库，
PyInstaller 漏带一个 DLL 时不报错，因为 System32 里恰好有。于是打包脚本逐个读产物里
每个 exe / dll / pyd 的导入表：导入的每个 DLL 要么随包带着，要么是每台 Windows 都自带的系统 DLL；
VC++ 运行库不算系统自带。删掉一个随包的 `vcruntime140.dll` 再审一遍，它会点名是哪些模块依赖它。

**给陌生人下载的包里，最不能出的错是带着自己的东西。** 两道闸：拿 `.env` 里每个密钥的**值**
逐字节搜整个产物（zip 要逐个成员解开再搜，压缩过的字节里搜不到明文），只报文件名不报值；
打 zip 之前清掉测试留下的运行记录和本机实测的能力缓存。

还有一道是人工的：演示包里带着一批真实运行的截图。逐张看的时候发现，其中一张最大化的浏览器截图上，
**收藏夹栏是开发机主人的个人书签**。换掉那次运行之后加了一道闸：每个要发出去的截图目录都得
记在"已人工审过"的清单里，连同内容哈希；换了运行或截图变了，打包就停，直到有人重新看过。
**不靠"下次记得看"。**

## 五、按真实用户的顺序验一遍

这一节的几个 bug 都是在写这篇文章的当天找到的，也最能说明"验证要贴着真实用法"。

打包版做完之后，我用它真跑任务，并且**严格按真实用户的顺序**：先打开被试网页，
然后在客户端里点"运行"；遇到确认卡片，先把客户端点到前台，再点"确认执行"。
这个顺序一天之内撞出了四个问题，没有一个是评测台或单元测试能撞到的。

**一、Agent 操作了它自己。** 视觉那一层找目标窗口只有两档 —— 显式指定的标题，否则"当前前台窗口"。
用户点"运行"的那一刻，前台就是客户端。于是 Agent 截了**客户端自己的界面**，在自己的运行列表上
点了两下，以为是在"推进任务"。评测台从终端起任务、总是先把浏览器开到前台，一次都没走到这条路上；
控件树那一层恰好多一档"任务里提到的应用名"，所以也没暴露。

**二、被自己挡住，于是"模拟"了一次审批。** 修完上一条，控件树那一层找对了窗口，
可路由时的遮挡检查发现目标窗口 100% 被压着 —— 压着它的正是客户端。这一层当场让步，
这一步被交给了写代码的那一层；而它碰不到网页，就写了一段"模拟审批"的代码，打印出「审批成功」。
系统里什么都没变，Agent 报告成功。路由理由里其实写着"产出不可轻信"，
但根子是 Agent 被自己的窗口挡住了。

修法：两层共用同一套窗口解析（显式标题 > 任务里提到的应用 > 前台窗口），不再各留一份；
前台窗口那一档**跳过 AutoMan 自己**，并把"换过人"写进路由理由；
**在路由的遮挡检查之前**就把目标窗口提到最前 —— 两层的点击都是按屏幕坐标真点下去的。

**三、每一次真人放行都被判成了拒绝。** 第二节说过：批准之后，内核要把前台交还给确认之前的窗口，
交还不了就按拒绝处理。可人刚在客户端上点了"确认执行"，前台此刻是客户端；内核是另一个进程，
Windows 的前台锁不许它把前台从客户端手里拿走。**安全网按设计生效了，于是没有一次放行能真正执行。**
确认流程的测试把"取前台窗口"换成了假函数，真实的前台锁一次都没碰到过。
修法是 Windows 为这件事准备的那个接口：此刻的前台进程（客户端）在送出"放行"之前，
调一次 `AllowSetForegroundWindow`，把设前台的权利交给这一个子进程。"交还不了就拒绝"那条保留。

**四、回放索引从来没有送到过界面。** 截 README 图时发现，演示包里那条失败的运行，回放里一张截图都没有。
追下去：后台算回放索引的任务，完成信号连的是一个 lambda；PySide 把 lambda 挂在**发送方**名下，
而发送方随线程池任务一起被删掉，跨线程排队的信号跟着丢了。记了截图指针的步照样能放，所以看着一切正常；
只有靠时间配对才找得回截图的历史步，一直是空的。前面那些覆盖率数字是直接调函数算的，
没走界面这条信号通路 —— **数字是对的，用户看到的是空的。**

同一天还修了一个同类的小问题：放映和使用手册都是盖满窗口的一层，确认卡片弹出来会被压在底下。

这些 bug 都不是"写错了一行"，而是**几个各自正确的设计，在真实用法里相遇了**：
"操作前台窗口"是对的，"被遮挡就让步"是对的，"交还不了前台就拒绝"也是对的。
单元测试各自守住了每一条，只有按用户的顺序完整走一遍，才会看见它们撞在一起。

修完之后，按同样的顺序重跑，全部由任务自己的确定性判据判定：
在**打包版**上，从 zip 解压到一个全新目录，客户端里读图表（视觉 + 代码）、照扫描件填表并提交
（视觉 + 控件树，提交前弹确认卡片，先把客户端提到前台再点确认），都通过；
在源码版客户端上，单据审批（控件树，同样走真人式确认）通过，
判据还核对了其余 24 张单据一个字段都没被动过。

## 小结

让人放心的不是某一个大机制，而是一串小的、具体的承诺，每一条都能被检查：

- 它能写的地方只有工作区，写之前有备份；
- 撤不回的事一定先问，默认是否，批准了也留痕；
- 它做过的每一步都能回放，推测的部分标明是推测；
- 装到你电脑上的那个包，在打出来之后被自己验过一遍 —— 按你会用的那种方式。
